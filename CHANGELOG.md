### Added
- `PRIVACY.md` completed (spec 4.3, 13.2): the approved wording in English, Arabic and French; who can read what; the relay's metadata in detail (padding, times, cleartext clock and counter, wake-up flag, hashed IP addresses); what is stored and when it is deleted; Cloudflare and Google FCM; retention and erasure; what the app keeps on the phone. `SECURITY.md` completed (spec 13.3): how to report, what the design protects and does not, and a threat model with every spec 13.3 case plus a hostile relay, a leaked FCM key, clocks, abuse and the supply chain, each with its honest limits. `scripts/check.sh` fails if the public docs use a forbidden privacy phrase.
- `PROTOCOL.md`: the v1 wire format (draft, implemented in v0.1.0): identity keys and device ID, pairing (X3DH adapted, QR payload, code path), safety number, Double Ratchet parameters, envelope layout and receive checks, HLC, event schema and versioning, attachments, relay request signing, constants, test-vector layout and known limits.
- `Crypto` interface and `SodiumCrypto` in `packages/mawaddah_protocol`: X25519, Ed25519, XChaCha20-Poly1305 (IETF), BLAKE2b and HKDF-SHA-256 from libsodium 1.0.22 (sumo) via the `sodium` 4.x package, whose build hook compiles libsodium (no system install). Typed keys; secrets in libsodium guarded memory with `dispose()`; key and nonce randomness from the injected `RandomSource` (`SodiumRandomSource` by default).
- Known-answer tests and vector files `test/vectors/rfc7748_x25519.json`, `rfc8032_ed25519.json`, `rfc5869_hkdf.json`, `rfc7693_blake2b.json`, `xchacha20poly1305.json`.
- Device identity (PROTOCOL.md sections 3 and 5): `DeviceIdentity.generate(crypto, random)` makes the Ed25519 signing key and the X25519 key independently (32 random bytes each, seed first); `toStorageBytes` / `fromStorageBytes` for the app's secure storage (65 bytes, versioned, input zeroed, `toString` redacted); `DeviceId` (`SHA-256("mawaddah/v1/inbox" || IKsig_pub)[0..16]`, base64url, strict `parse`); `safetyNumber` (20 digits, same in both orders) and `safetyNumberGroups`.
- `tool/gen_vectors.dart` and generated vector files `test/vectors/identity.json` and `safety_number.json` (deterministic seeds written into each case).
- Pairing key agreement (PROTOCOL.md section 4): `PairingInitiator` and `PairingJoiner` (injected `Crypto`, `RandomSource`, `Clock`), `PairingBundle`, `PairingQr` (129 bytes, `MAWADDAH:` + base64url, strict decoding), `PairingReply`, the HKDF derivation of `SK`, `KC`, `TH`, `confirm` and `AD`, `PairingResult` (shared keys, safety number, "must be confirmed" state on the code path) and `PairingProfile` for the encrypted profile events. A slot lasts 10 minutes and takes one reply.
- `Crypto.hmac` / `verifyHmac` (HMAC-SHA-512-256, libsodium `crypto_auth`), tested with RFC 4231 cases (`test/vectors/rfc4231_hmac.json`).
- Generated vectors `test/vectors/pairing.json` (13 cases); `.gitleaks.toml` allowlists it and `rfc4231_hmac.json` by exact path.
- Double Ratchet chains (PROTOCOL.md section 6): `RatchetSession.fromPairing` (joiner = Alice, sends first; initiator = Bob, `canSend` only after the joiner's first message), `initAlice` / `initBob`, `encrypt` / `decrypt` with `RatchetHeader` (`dh_pub || pn || n`, 40 bytes) and the 50 envelope bytes before it, so the AEAD authenticates `AD || envelope bytes[0..90]`. A DH ratchet step happens on every turn change; a failed decrypt (`RatchetException`) leaves the session unchanged. In-order delivery per direction only: a message that needs a skipped key is refused (`skippedMessage`) until #14.
- Generated vectors `test/vectors/ratchet.json` (a 16-step conversation with turn changes and crossing messages; every key and ciphertext derived twice in the generator); `.gitleaks.toml` allowlists it by exact path.
- Skipped message keys for the Double Ratchet (PROTOCOL.md section 6, Signal 3.5): messages may arrive out of order or late, also across turns. One message may create at most 1,000 skipped keys (`maxSkip`, both chains of a turn together; more is refused with `tooManySkipped`). At most 1,000 are stored, oldest deleted first. A key older than 30 days (injected `Clock`) is ignored and then deleted, at the next success or by `deleteExpiredSkippedKeys()`. A failed decrypt still changes nothing, including the stored keys.
- Saving a ratchet session: `RatchetSession.toStorageBytes` / `fromStorageBytes` (versioned local format, input zeroed, damaged bytes refused with `FormatException`) and `save` / `load` through `Storage`. `ratchet.json` gains an out-of-order case (28 steps).
- Signed envelopes (PROTOCOL.md sections 7 and 8): `Envelope.seal` (pad to 256-byte blocks, ratchet-encrypt with the 50 envelope bytes as associated data, Ed25519 signature with the `mawaddah/v1/envelope` label) and `Envelope.open`, which checks in the order of section 8: structure, addresses, signature, replay window, time window, decryption, padding. Failures are `EnvelopeException`s whose `EnvelopeFailure` says whether to acknowledge the envelope and whether to keep its raw bytes; only `undecryptable` changes state (the counter is used up). `Envelope.parse` reads the fields.
- `ReplayWindow`: the RFC 4303 sliding window over envelope counters (`W = 1024`), with versioned save/restore bytes (137 bytes, local format).
- Hybrid logical clock (PROTOCOL.md section 9): `Hlc` (48-bit milliseconds + 16-bit counter; 8-byte and 16-hex-digit forms) and `HlcClock` (`send`, `receive`) over the injected `Clock`; always increasing when the clock goes back.
- `Uuid7.generate` / `isValid` (RFC 9562) from the injected `Clock` and `RandomSource`.
- `Crypto.pad` / `unpad` (libsodium `sodium_pad`, ISO/IEC 7816-4) and `InvalidPaddingException`; `DeviceId.fromBytes`.
- Generated vectors `test/vectors/envelope.json` (3 sealed envelopes, 13 rejected cases), `hlc.json` and `uuid7.json`; `.gitleaks.toml` allowlists `envelope.json` by exact path.
- Event model and apply (PROTOCOL.md sections 10 and 11): `Event` with strict v1 JSON, `EventBatch.encode`/`decode` for the envelope plaintext (`EventException`: `malformed`, `wrongAuthor`), `EventStamp` (order `hlc`, author bytes, `event_id`), `EventFactory`, `EntityRegistry.v1` (`device` hello and `profile` payload checks; `message`, `reaction`, `receipt` rules), the `EventStore` interface with `InMemoryEventStore`, and `Applier` (`applyReceived`, `applyLocal`, `reapplyUnapplied`): idempotent, field-level last-writer-wins, append-only, final tombstones that purge payloads, unapplied events with a reason and a stream. `protocolVersion` / `minSupportedProtocol` constants.
- Generated vectors `test/vectors/event.json` (encoding, refused plaintexts, three apply scenarios).
- Outbox and sync loop (PROTOCOL.md section 17): `SyncEngine` with `commitLocal` (apply and queue in one transaction) and `syncOnce` (one run at a time: fetch after the stored cursor, open, apply and commit each envelope with its cursor, then a cumulative ACK; repeat a lost ACK; leave envelopes from the future on the relay and report the wrong-time warning after 24 h; then send the outbox). A failed deposit is repeated as the same sealed bytes, so retries use no extra counter or ratchet key; a sealed envelope older than 1 day is sealed again. `SyncReport` (counts only; the relay error as a type name), `BackOff` (5 s doubling to 15 min, advisory), `WakePolicy.v1` (one table: `message` `create` wakes). `SyncStore` interface with `SealedEnvelope` and `UnappliedEnvelope`, and `InMemorySyncStore`, which shares the `InMemoryEventStore` transaction.
- Compaction (spec 4.6, PROTOCOL.md sections 10 and 17): `Compactor` replaces the logged events of an entity type with one local `snapshot` event (payload `{"replaced": n}`) once there are 5,000 (`compactIfNeeded`, or `compact` for one type), in one transaction; the merged state is unchanged and no dropped payload or replaced value stays in the log. `SyncEngine` compacts at the end of each run (`compactAfter`, default 5,000) and saves the HLC; `SyncReport.eventsCompacted`. `EventStore` gains `loggedEventCount` and `dropLoggedEvents` (the IDs of dropped events stay, so `containsEvent` still spots late copies), implemented by `InMemoryEventStore` (`droppedEventIds`). Snapshots never leave the phone; a received one stays unapplied (unknown op). No wire change, no new vectors.
- Relay request signing in the Dart package (PROTOCOL.md section 13): `RelayRequestSigner` (`sign` returns the four `Maw-*` headers from the injected `Clock` and `RandomSource`; `signingInput` builds the six signed lines and refuses inputs the relay could not match). Generated vectors `test/vectors/relay_signing.json` (4 cases), checked by both the Dart and the relay tests; `.gitleaks.toml` allowlists it by exact path.
- Relay: signed-request checks (headers, ±300 s clock window, Ed25519 signature with WebCrypto, nonces remembered 15 minutes per key), `POST /v1/inbox` (inbox ID computed from the signing key; stores only the key, push token and platform; a repeat from the same key is idempotent), 5 new inboxes per IP per hour (IPv6 per /64; state deleted one hour after the last registration), JSON errors with stable codes and no internal details. Two SQLite-backed Durable Objects, `DeviceObject` and `RegistrationLimitObject`, with alarms that delete expired state. `relay/README.md` documents the endpoints, error codes, what is stored and the dashboard settings that keep request logs off.
- Relay pairing slots (spec 4.5, PROTOCOL.md section 4.5): `POST /v1/pairing-slot` (signed by the bundle's key, which needs an inbox; the bundle signature is verified; 10 minutes, single use; returns `slot_id`, a uniformly random 6-digit `code` unique among live slots, and `expires_at`; a retry with the same bundle gets the same slot), unsigned `GET /v1/pairing-slot/{slot_id or code}` (at most 5 code lookups per IP per 10 minutes that find no open slot; each is counted before the lookup and given back if it finds one, so parallel guesses cannot pass the limit), `POST /v1/pairing-slot/{slot_id}/reply` (first reply wins, later ones get `slot_used`) and the signed `GET /v1/pairing-slot/{slot_id}/reply` for the initiator, which erases the bundle and reply. New Durable Objects `PairingSlotsObject` (one for all slots) and `LookupLimitObject` (migration `v2`); new error codes `inbox_required`, `slot_not_found`, `slot_used`, `slot_conflict`, `slots_full`. Relay tests replay the Dart `pairing.json` bundles and replies.
- Relay inbox routes (spec 4.5): `POST /v1/inbox/{id}/allow` (the owner allows exactly one sender key; another key gets `allow_conflict`), `PUT /v1/inbox/{id}/envelopes` (raw envelope bytes, at most 65,536, from the allowed sender only, header `Maw-Wake: 0|1`; at most 100 MiB waiting per inbox), `GET /v1/inbox/{id}/envelopes?after=cursor` (deposit order, opaque increasing cursors never reused, pages of at most 100 envelopes and 1 MiB with a `more` flag), `POST /v1/inbox/{id}/ack` (cumulative: deletes every envelope up to and including the cursor), `POST /v1/inbox/{id}/push-token` and `DELETE /v1/inbox/{id}` (inbox, allowed sender and envelopes; idempotent). Only the owner may fetch, acknowledge, change the token or delete. A cursor never handed out is refused (`invalid_cursor`). New error codes `inbox_not_found`, `not_inbox_owner`, `sender_not_allowed`, `allow_conflict`, `inbox_full`, `invalid_cursor`.
- Relay blobs (spec 4.5, PROTOCOL.md section 12): `PUT /v1/inbox/{id}/blobs/{blob_id}?size=…&chunk=…` (from the allowed sender, in order, 1 MiB chunks, at most 10 MiB per blob, 100 MiB of blobs per inbox reserved at the first chunk; a repeated chunk with the same bytes is idempotent), `GET …/blobs/{blob_id}?chunk=…` (owner, complete blobs only, `Maw-Blob-Size` header) and `DELETE …/blobs/{blob_id}` (the owner's ACK, or the sender giving up an upload). Blobs are stored in the receiving device's Durable Object; `DELETE /v1/inbox/{id}` deletes them too. New error codes `blob_not_found`, `blob_too_large`, `blob_quota_exceeded`, `blob_conflict`, `chunk_out_of_order`, `blob_incomplete`. `relay/README.md` gives the storage choice and its cost.
- Relay 30-day hard delete: envelopes and blobs are deleted 30 days after they were stored, on every access to the inbox and by the device object's alarm, which is now set for the first item to expire (nonce, envelope or blob) whenever something is stored.
- Relay tests: unit tests over Node's `node:sqlite` with a fake clock, and integration tests against the Worker in wrangler's local runtime. New dev dependency `@types/node` (tests only).
- Relay FCM wake-ups (spec 4.5, 8.7): after a deposit with `Maw-Wake: 1` is stored, one FCM HTTP v1 data message, high priority, collapse key `s`, data exactly `{"t":"s"}`, sent after the answer (`waitUntil`) and never retried. The Worker signs the Google service-account JWT itself (RS256, `firebase.messaging` scope) from the secret `FCM_SERVICE_ACCOUNT`; Google's addresses are fixed in the code; the access token is cached until 5 minutes before it expires. An `UNREGISTERED` answer deletes the inbox's push token unless the phone has sent a new one. Without the secret, no wake-ups are sent.
- Dart relay client (spec 4.5, 14b.3): `HttpRelayClient` over `package:http` for every relay route, signed with `RelayRequestSigner`, base URL injected (HTTPS; plain HTTP only to a local relay). Typed errors: `RelayException` with `RelayErrorCode` (the relay's stable codes plus `network`, `timeout`, `bad_response`, `invalid_response`, `unknown`), `retryable`, `retryAfter` (at most one hour), `serverTime`, `nextChunk`. Passing faults are retried after 1 s and 3 s, except a deposit, the reply read and a code lookup; refusals are left to the caller's back-off. Answers are checked (inbox ID from the key, increasing cursors, canonical base64url, exact chunk sizes, size limits, no redirects); one that parses but breaks the rules is `invalid_response` and is not retried. `uploadBlob` / `downloadBlob` over the chunk routes. `PairingInitiator.identity` for signing the attempt's requests. Helpers `encodeRelayId`, `decodeRelayId`, `isRelayId`, `relayBlobChunkCount`.
- `scripts/relay-integration.sh`: starts the relay with `wrangler dev`, runs the Dart client's integration tests against it, stops it; part of `scripts/test.sh` and CI.
- New dependency `http` (Dart team, HTTP client).

### Changed
- `package:crypto` moved from dev to normal dependencies: the device ID and relay body hashes need SHA-256, which the `sodium` Dart API does not offer (ADR 0006 point 3).
- `RatchetSession.fromPairing`, `initAlice` and `initBob` now take a `Clock`. `RatchetFailure.skippedMessage` is replaced by `tooManySkipped`, because out-of-order messages are now accepted.
- `Storage.write` must not keep a reference to the value it is given (callers zero secrets once it completes).
- `PROTOCOL.md` clarifications from building the envelopes (wire format unchanged): the `version` and `type` bytes are read before the v1 length rules; a v1 envelope whose `L` is not a multiple of 256 plus 16, or whose counter is 0 or above 2^63 − 1, is malformed; bad padding after decryption counts as `undecryptable`; a full HLC counter moves the physical part on by 1 ms instead of waiting; the UUID v7 byte layout is written out.
- `PROTOCOL.md` section 13 (wire format unchanged): the order of the relay's checks and its error codes, and the path line is the path and query as the relay's runtime parses the URL, so clients send paths that need no normalising. Section 16 names the per-network registration limit.
- Relay: a wrong method on `/health` now answers `405` with the JSON error `method_not_allowed` (it had an empty body).
- `RelayClient` covers every relay route: `registerInbox`, `createPairingSlot`, `lookupPairingSlot`, `replyToPairingSlot`, `readPairingReply`, `allowSender`, `putBlobChunk`, `getBlobChunk`, `deleteBlob`, `setPushToken`, `deleteInbox`; `fetch` returns a `RelayPage` with the relay's `more` flag. `FakeRelayClient` follows it: made with a signing key it applies the relay's rules and error codes (owner, allowed sender, slots, cursors, pages, blob order and quotas), and `as(key)` gives the partner's client on the same state; `failNext` injects errors.
- `SyncEngine` stops fetching when the relay says nothing more waits (no extra empty fetch), and `SyncReport.relayError` is the relay's error code for a `RelayException`.
- `SyncStore.unappliedEnvelopes` orders envelopes with the same time by cursor as a number (`"99"` before `"100"`); the text order was only right for the old zero-padded fake cursors.
- `mawaddah_protocol` now needs Dart 3.13 or later (required by `sodium` 4.x) and a C compiler the first time it is built or tested.
